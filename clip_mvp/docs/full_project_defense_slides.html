PROBLEM02 / 16
项目背景与痛点

长视频二创不是单点 AI 问题，而是跨工具、跨时间轴的工程问题

人工成本高

看视频、扒字幕、写文案、录配音、剪画面和导出文件需要在多个工具之间切换。

信息容易漂移

人物、队伍、左右方、时间节点复杂，单靠模型生成容易写错事实。

核心矛盾

语义判断很适合交给 AI，但最终视频必须落在确定的文件、状态和时间轴上。

音画同步难

解说短视频必须让旁白、画面和字幕共用一条稳定时间线。

修改成本高

文案或配音一变，人工剪辑通常要重新移动大量片段。

DRAFT REVIEW08 / 16
文案生成与人工审核

文案阶段生成的是“可审核结构”，不是直接黑盒成片

raw subtitles

ASR 识别出的原视频字幕，作为内容证据。

→

draft beats

LLM 生成结构化解说段落和 grounding。

validation

解析 JSON、归一化字段、检查长度和证据。

↻

repair

必要时让 LLM 修复格式或结构问题。

human review

用户编辑整体文案和每个 beat。

→

reviewed beats

确认后成为配音和选片的唯一依据。

两种模式

AI 解说模式会生成文案；定稿文案模式只做 beat 拆分，不主动改写正文。

关键约束

用户确认后的文案不再被后端静默改写，避免审核失效。

为什么保留人工

LLM 在事实、人物和时序上会有不确定性，人工审核是内容质量的最终闸门。

KNOWLEDGE09 / 16
知识库与本次补充事实

长期知识负责背景，单次事实负责硬约束；冲突时以本次补充事实为准

本次补充事实

例如“蓝色方 WBG，红色方 AL”，只作用于当前任务。

用户任务要求

目标风格、目标时长、叙事重点和输出要求。

项目知识库

长期复用的人物、队伍、术语和背景设定。

原视频字幕

ASR 提供事件证据，但识别结果也可能有噪声。

为什么分开设计

左右方、阵容、临场事件等信息不应该污染长期知识库；长期知识也不能覆盖单个视频里的明确事实。

上下文快照

任务创建时将知识库和补充事实合并进 project_context，使后续生成和选片使用同一份上下文。

设计价值

通过上下文优先级和任务级事实隔离，降低模型在人物、阵营、时间和术语上的事实漂移。

FINALIZE10 / 16
配音、选片与渲染

成片阶段的关键是把文案、配音、画面、字幕锁到同一条时间线

01 VOICE按 beat 生成配音读取每段真实 voice_duration_ms，而不是按字数估算。
02 SELECTLLM 选择画面用 reviewed beats、配音时长、全量字幕和上下文选原视频片段。
03 VERIFY后端校验检查数量、顺序、边界和时长误差，失败时给出问题段落。
04 RENDERFFmpeg 渲染剪切、拼接、混音、生成时间线和字幕。
05 BURN字幕烧录单行字幕居中展示，导出 ASS/SRT 并烧录进 MP4。

RISKS15 / 16
技术难点与解决方案

我们主要解决四类风险：模型、时间轴、环境、长任务

LLM 输出不可控

通过 prompt、JSON schema、字段归一化、grounding、repair 和人工审核兜底。

音画字幕错位

以真实配音时长约束选片，后端校验片段时长，最终字幕跟随旁白时间轴。

多工具结果一致性

ASR 字幕、LLM 文案、TTS 配音和 FFmpeg 时间线来自不同工具，需要统一字段、单位和时间基准。

长任务状态管理

后台 worker、任务状态表、事件日志和前端轮询让用户知道执行到哪一步。
